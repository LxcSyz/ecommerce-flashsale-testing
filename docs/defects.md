# 缺陷报告与回归证据

## BUG-LAB-001：检查库存与扣减分离导致超卖

类型：人为构建的教学缺陷样例，位于 `scripts/reproduce_oversell.py`；不是声称在第三方线上系统发现的缺陷。严重程度：在交易业务中属于严重数据一致性问题。

前置条件：初始库存 10，24 个线程各购买 1 件。运行：

```bash
python scripts/reproduce_oversell.py
```

缺陷路径：各线程先读取库存，再通过屏障让所有线程读完，随后各自进入写事务，无条件执行 `stock = stock - 1` 并写预占记录。屏障是为了稳定复现某一种合法的危险时序，不代表真实请求必定总以此顺序到达。

预期：最多创建 10 条预占记录，剩余库存为 0。

实际（2026-11-09 本机实测）：创建 24 条预占记录，剩余库存 -14，超卖 14 件。原始证据：运行生成的 `reports/defect-replay.json`。

根因：库存校验与扣减之间存在竞争窗口；先前读到的库存不再有效。单独给 UPDATE 加事务仍不足以保护事务外的 SELECT。

修复：在读取业务条件前开启 `BEGIN IMMEDIATE`；执行 `UPDATE ... WHERE stock > 0`，依据受影响行数决定是否成功；预占记录与库存修改同事务提交。修复样例实际成功 10、剩余 0、超卖 0。

应用层另有 `CHECK(stock >= 0)` 兜底；缺陷样例故意没有此约束，以展示根本问题，不能把加约束导致的异常当成完整业务修复。

回归：`test_24_buyers_compete_for_10_items` 使用实际 HTTP、独立用户、应用数据库；断言 10 个 201、14 个 OUT_OF_STOCK、10 条订单、库存 0 和库存守恒。

## 防御场景回归

以下是风险场景的验证记录，不冒充另行发现的真实缺陷：

| 风险 | 可能原因 | 当前防护与回归 |
| --- | --- | --- |
| 同一用户绕过限购 | 在事务外统计历史购买 | 写事务内检查有效订单；12 路请求仅 1 成功 |
| 请求重试重复扣库存 | 幂等查询与创建之间有竞争 | 写事务 + 用户/键唯一约束；12 路同键返回同一订单 |
| 取消订单多次回补 | 先查询状态再在事务外回补 | 状态与回补同事务；12 路取消仅回补 1 件 |
| 支付和取消都成功 | 缺少互斥状态转换 | 同事务校验状态；一个成功、另一个状态冲突 |
| 多商品部分扣减 | 每个商品各自提交 | 整单事务回滚；第二商品失败不改变首商品 |

本实验展示单进程多线程 + SQLite 的一致性。分布式架构需要重新设计并验证库存原子操作、数据库与缓存一致性、消息幂等和补偿，当前项目未实现这些能力。
