# 面试展示指南

## 5–8 分钟演示

1. **业务规则（1 分钟）**：说明预占库存与最终状态。指出金额使用分、普通与秒杀入口分开，取消会恢复库存并释放限购。
2. **正常流程（1 分钟）**：启动 `python -m app.server`，注册账号，加一个键盘，下单并模拟支付，展示库存 100 → 99。创建另一订单再取消，展示回补。
3. **自动化（1–2 分钟）**：运行 `python -m pytest -v`，选看越权、多商品回滚、幂等和并发测试源码。展示真实 JUnit / Allure 原始结果。
4. **缺陷分析（1–2 分钟）**：运行 `python scripts/reproduce_oversell.py`，对照 24 成功 / -14 库存与 10 成功 / 0 库存，讲明人为控制时序的目的和事务边界。
5. **工程化与边界（1 分钟）**：展示 CI、浏览器测试、压测脚本和数据库守恒校验，说明 SQLite 单机写事务限制。

演示前创建新数据库可以重置业务数据而不用删除旧文件：

```bash
python -m app.server --port 8001 --db data/interview-01.db
```

如果复用旧数据库，秒杀可能已结束或库存已被占用；改用一个尚不存在的数据库文件即可获得新活动。

## 可以据实使用的项目描述

> 独立完成电商交易与秒杀库存测试实践，搭建可本地运行的被测系统，设计认证、订单状态、权限隔离和并发库存用例；实现 Pytest 接口回归及 Playwright 核心流程，配置 GitHub Actions。通过 24 用户竞争 10 件库存验证超卖防护，结合数据库校验订单与库存一致性，并在隔离实验中复现和分析超卖原因。

将“独立完成”调整为符合你实际参与程度的表述。理解和亲自运行代码后再放入简历，不把教学实验写成商业上线经验。Locust 和 CI 的表述应与你自己实际运行的结果一致。

## 常见追问

**为什么不仅检查 HTTP 200/201？** 返回成功不等于数据正确。检查订单数量、状态、金额、剩余库存以及有效订单占用，才能验证副作用。

**为什么不用固定 sleep 制造并发？** sleep 不能保证所有线程处于同一竞争阶段。屏障让请求集中开始；缺陷样例另用读屏障控制特定危险时序。应用回归只在请求起点同步，不干预内部代码。

**事务为什么从读取之前开始？** 先读再开事务会让判断建立在过期快照上。SQLite 的即时写事务把读取、校验、扣减、订单写入和回补放在同一串行化边界内。

**限购与幂等有什么区别？** 限购是用户业务规则，幂等是同一操作的重试语义。用户换键不能绕过限购，同键重试也不应被限购挡住，所以先处理已成功请求的幂等重放。

**如何测取消与支付竞争？** 同时发出两个操作，断言一个 200、另一个 409；若支付获胜库存保留扣减，若取消获胜库存回补。

**为什么不用 Redis？** 当前目标是用较小系统证明测试设计与一致性验证能力。引入 Redis 后需额外验证缓存与数据库之间的一致性和失败补偿，不能仅增加技术名词。

**还能继续补什么？** 自动关单及其与支付竞争、服务端登出撤销令牌、持久化库存流水、精确活动边界的可控时钟测试，以及独立负载机上的阶梯压测。这些尚未实现，面试时应明确区分。
